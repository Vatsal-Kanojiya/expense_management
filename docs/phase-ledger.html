Say this out loud in an interviewReach for a queue when the trigger is a request. When the trigger is a clock, a command plus cron is usually the honest answer.

Drew blood — and all 16 tests stayed greenThe digest iterated users with queryset.iterator() (a server-side cursor) while committing inside the loop. The commit invalidates the cursor; user two raises InterfaceError. Every TestCase passed, because TestCase wraps each test in a transaction so atomic() is only a savepoint and never really commits. It surfaced only when the command was run for real. TransactionTestCase now pins it — the clearest demonstration in this project of why both base classes exist.

Two rules that prevent the classic bugsTasks take primary keys, never model instances — arguments are JSON on the broker, so an instance either fails to serialise or arrives stale. And dispatch with transaction.on_commit, never .delay() inline: the worker is fast enough to query for a row the web process has not committed.

Each Celery setting is a failure modeJSON-only serialisation (pickle turns broker write access into RCE on every worker) · acks_late (a killed worker redelivers — the price is that tasks must be idempotent) · prefetch_multiplier=1 (with acks_late, a worker holding ten prefetched tasks redelivers all ten when it dies) · autodiscover_tasks (without it the worker starts fine and fails at call time with "unregistered task").

The invariant a database cannot holdLine items must sum to the expense total. Drew blood — the dangerous one.distinct() does not fix an aggregate. DISTINCT removes duplicate rows from a result set; the aggregate has already eaten them. And the failure returns a plausible wrong number, not an error — nothing tells you it happened.

State this properly, onceForward FK or one-to-one → select_related: one query, a JOIN widens the row. Multi-valued (reverse FK, M2M) → prefetch_related: a second query, because a JOIN would multiply rows instead of widening them. The expense list uses both.

Why Subquery, not Max“Last spend: ₹120 on 1 Mar” cannot be two aggregates — Max(spent_on) and Max(amount) pair the latest date with the largest amount and print a combination that never happened. Subquery selects one row and reads fields off it; OuterRef("pk") is the correlation. Note a Subquery inherits no scoping from the queryset it annotates.

Drew bloodFiltering on an annotation is not the same as filtering on the relation again. .filter(items__isnull=False) after .annotate(Sum("items__amount")) adds a second join, which multiplied rows and made every un-itemised expense report as broken. Sum over no rows is NULL, so .filter(items_total__isnull=True) already answers it with no extra join.

Three more worth carryingF() keeps a comparison in the database — there is no Python value that means “this row's amount”. only()/defer() can create the N+1 they exist to avoid, because a deferred field is lazy, not missing. And exists() can stop at the first match where count() must scan, while if queryset: evaluates and caches every row.

The other half of phase 8's tradeAn invariant that moved into a form is one the database cannot hold — so the admin, a shell, a data migration or an older version of the code can violate it silently. check_splits is the audit command that reads the rows at rest.

The lost update, prevented

Settling a balance is a read-then-write. Two requests read 150 outstanding, both write, and a 150 debt is repaid 300.

session 14858b503race proved in both directions

Concepts

Why no constraint can catch itTwo genuine settlements of the same amount on the same day are perfectly legal. The lock is the only answer. select_for_update goes on the participant row — which is not modified; it is the lock, because the thing needing protection is a number derived from four tables and has no row of its own.

Verified in both directionsWith the lock: one settlement of 150. With the line deleted: 300 repaid, and the test fails. A concurrency test that has never been seen to fail is not evidence of anything.

The savepoint rule, corrected mid-phaseCatching an exception outside an inner atomic() does not poison the outer block — that block is a savepoint and has already rolled back cleanly. What poisons a transaction is catching a database error with no savepoint between it and the outer block. Which is why every constraint test reads with self.assertRaises(IntegrityError), transaction.atomic():.

Why phase 12 had to come firstselect_for_update is a no-op on SQLite, which locks the whole database rather than individual rows. Running this phase first would have taught the API without the behaviour, and the race test would have passed for the wrong reason.

Built, demonstrated, rejected@cache_page keys on the URL and nothing else — so every signed-in user requesting / is served whatever the first one put there. There is a test that builds it and shows one user receiving another's page: the view never runs for the second user. Frappe's cache API is key-based, with no page-cache decorator to misuse.

Why bump a version, not delete keysKeys carry user id + date range + a version stamp. Deleting “the right keys” on write would mean knowing every date range anyone has ever viewed. Bumping a stamp invalidates them all in one atomic incr.

Drew bloodDjango does not clear the cache between tests. A cached dashboard survived into an unrelated test and made its pinned query count wrong — 2 queries where 8 were expected. A test that caches by accident passes for a reason nobody chose. Caching is now off in tests by default.

LocMemCache is per-processWhich makes it wrong under gunicorn with three workers: each holds its own copy, and a bump in one never reaches the others. It stays the default only so a fresh clone runs without Redis. Compose gives the cache a third Redis database index, separate from broker and result backend, so flushing the cache cannot take the queue with it.

The cautionary tale of the phaseThe context processor's first version counted balances — which walks every expense. A context processor runs on every single template render, so that added four to six queries to every request in the project and broke three pinned query counts. It now only ever reads a cached value; the balances page populates it as a side effect of work it already does. The signal rule this project settles onA signal is right when the concern is cross-cutting, invisible by nature, and must not be forgotten. Cache invalidation and audit logging qualify. “Create a related row when this one is saved” does not — that is business logic hiding from its caller. Frappe's doc_events is the direct analogue and gets used far more freely.

What the signal cannot seebulk_create fires no signals — it operates on rows, not instances. A test asserts that limit rather than leaving it to be discovered.

ContextVar, not threading.localUnder ASGI one thread interleaves many requests, and a thread-local would leak one request's id into another's log lines. Frappe is WSGI-only, so the distinction never surfaces there.

Hand-written, because the key is the designA library hides the one decision that matters. By address alone, one office behind one NAT is one blocked building. By username alone, an attacker locks any account out of its own login for free. By both, a single source against a single account is slowed — which is the shape of credential stuffing. (django-axes is the right answer in production; this is the right answer for learning.)

What it does not do — written in the moduleIt does not stop a distributed attack, and its fixed window allows up to 2× the limit across a boundary. A sliding window costs a sorted set per key and is not worth it at this scale. Stating the limits is part of shipping the feature.

Verification with no model and no columnPasswordResetTokenGenerator subclassed with is_active mixed into the hash, so the link self-invalidates on use with nothing stored. Subclassing rather than reusing is what stops a verification link being replayed as a password-reset link.

Why not just change on_deleteCASCADE would remove the protection that stops a category being deleted out from under a year of expenses. SET_NULL would make the column nullable, so every query and template handles a category-less expense forever, to solve a problem that happens once per account. The test asserting that plain user.delete() still raises is kept, so nobody deletes this module as redundant.

The modelling decisionSelf is a Participant(is_self=True) row, not a boolean on Expense. A boolean answers only “is the owner in this split” — it cannot answer “who paid”, because a payer needs an identity and a boolean has none. Making self a participant unifies payer and consumer into one model: one dropdown, one set of validation rules, one balance engine, zero special cases. The reversal test is written down — go back to the boolean if the is_self special-cases ever exceed three or four.

Signed, not directionalSettlement.amount is now signed with a != 0 constraint: positive means they paid you, negative means you paid them. The alternative — a direction field — makes every aggregate branch on it, and one missed branch silently double-counts. Outstanding stays a single expression: balance − sum(settlements).

Drew blood — every line item vanishedFill in line items, tick who shared each, leave the note blank, submit: the error came back and all the items were gone. The POST carried them; the server threw them away. A CreateView has two exits that share no code — form_valid() got the bound formset, form_invalid() fell through to get_context_data, whose fallback built a fresh empty one. The comment beside that fallback claimed form_invalid passed a bound formset, which is how the bug survived review from phase 8 until now.

And the fix that was refusedNo persistence was added, and adding some would have been wrong. Session storage, localStorage or a draft table would each be a second copy of state that already exists in the POST — and a second copy can disagree with what was submitted. Re-render from the request.

Drew blood — the migration that crashedThe self participant was first named "You", which collides with the case-insensitive unique name constraint for anyone who already had a contact called that — and in a data migration that collision stops the whole upgrade. Renamed to FirstName (self) with a numeric suffix. Migration 0008 was corrected in place and 0010 renames the rows the old one created: normally editing an applied migration is wrong, and the reasoning for why it was acceptable here is written down.

Drew blood — the scoping lesson, sixth appearanceThe API accepted another user's participant as paid_by. Same lesson as phase 3's dropdown, phase 8's multi-select and phase 10's list action — a new entry point is a new place to forget the filter. Alongside it: ticking only Rahul charged him the whole bill, because the owner was no longer counted by default; the API now adds self unless include_self=false.

A has_changed() trap, caught before shippingPre-selecting the owner on blank line rows makes every blank row differ from “nothing” — so a removed or untouched row would count as filled in and fail on its empty name. has_changed() now looks only at name and amount for unsaved rows. A formset skips an extra form that comes back unchanged, so an empty row is no row.

Formsets, the interesting halfA saved row cannot be torn out of the DOM — Django deletes it only if its DELETE flag comes back ticked and its hidden id is posted, so the row is hidden, not removed. An unsaved row is blanked instead, because removing it leaves a hole in the index sequence, and closing that hole means rewriting the name, id and label of every field on every surviving row.

Every script enhances markup that already works without it.
