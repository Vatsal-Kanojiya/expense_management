deepphase-2-auth · phase-16-hardening

1 · Auth, sessions and permissions

Your biggest gap, and you flagged it yourself. Frappe hands you User, roles and has_permission as furniture; Django gives you primitives and expects you to assemble the policy.
What deep means
  • Session auth end to end: what login() writes, where the session lives, what the cookie holds, how AuthenticationMiddleware puts request.user there
  • AbstractUser vs AbstractBaseUser vs PermissionsMixin — when each is right
  • AUTHENTICATION_BACKENDS, and writing one (login-by-email is the classic exercise)
  • Password hashing: PASSWORD_HASHERS, why set_password exists, why a plain ModelAdmin on a user model is a security bug
  • Model permissions vs object-level permissions — Django's built-ins are per model, not per row. Your OwnerScopedMixin is object-level authorisation done by hand
  • Session vs token vs JWT, and when each is appropriate
Answer cold
  • “A user logs in. Walk me from POST to the next request being authenticated.”
  • “How do you restrict a view to only the rows the current user owns?”
  • “Why 404 rather than 403 for another user's record?”
  • “Add login-by-email without breaking username login.”

Your storyRate limiting, hand-written in forty lines because the keying decision is the whole design and a library hides it. By address alone, one office behind one NAT is one blocked building. By username alone, an attacker locks any account out of its own login for free. By both, credential stuffing gets slowed — and the module states what it still does not stop.

deepphase-5 · phase-9 · phase-12

2 · The ORM and query performance

The most-asked Django topic by a wide margin, and the easiest place to look junior — a candidate who cannot spot an N+1 is filtered fast. Frappe's get_list hid all of it from you.
What deep means
  • Querysets are lazy — when does a query actually execute, and what causes a second one
  • select_related (JOIN, forward FK) vs prefetch_related (second query, M2M and reverse FK) — and why they are different mechanisms rather than one flag
  • annotate vs aggregate; values() before annotate() as the GROUP BY switch
  • F() to reference a column and dodge a race; Q() for OR and NOT
  • Subquery / OuterRef / Exists — the step up from filtering
  • only() / defer(); exists() vs count() vs truthiness
  • Reading print(qs.query) and an EXPLAIN plan
Answer cold
  • “This page makes 200 queries. Find out why and fix it.” — the most common practical task there is
  • “Increment a counter safely under concurrency.” → F(), not read-modify-write
  • “filter().exclude() vs filter(Q(…) & ~Q(…)) — same result?”

Your storySearch across items and people crossed a multi-valued relation and the total came back as 1800 for a 900 expense. .distinct() does not fix an aggregate — DISTINCT removes duplicate rows, but Sum() has already eaten them. The fix aggregates over the distinct set of pks via a subquery. The failure returned a plausible wrong number, never an error.

deepphase-15-internals

3 · Request/response lifecycle and middleware

Frappe hides the whole pipeline. Interviewers use this to separate people who use a framework from people who understand one — and it is the frame that makes auth, CSRF and sessions click.
What deep means
  • WSGI/ASGI entry → middleware chain → URL resolution → view → template → response, and back out through middleware in reverse
  • Writing custom middleware, and why AuthenticationMiddleware must come after SessionMiddleware
  • What CsrfViewMiddleware checks, and why the token is per-session
  • Where exceptions are caught
Answer cold
  • “What happens between the browser sending a request and your view running?”
  • “Write middleware that logs slow requests.”
  • “Why does middleware order matter? Give an example of a wrong order.”

Your storyThe nav-badge context processor counted balances — and a context processor runs on every single template render, so it added four to six queries to every request in the project and broke three pinned query counts. It now only reads a cached value. Pair it with the request-id middleware, which uses ContextVar rather than threading.local because under ASGI one thread interleaves many requests and a thread-local leaks one request's id into another's logs.

deepphase-3-crud

4 · Class-based views and the MRO

You already use these, which makes them fair game for deep follow-ups. “I used ListView” invites “what does it do?” — and having no answer is worse than having used a function view.
What deep means
  • as_view() → dispatch() → get/post
  • Where get_queryset, get_context_data, get_form_kwargs and form_valid sit in that chain
  • Why mixin order matters and how Python's MRO resolves it
  • When a CBV is the wrong choice — a strong answer names cases where a function view is clearer
Answer cold
  • “Walk me through what ListView does between the URL match and the template rendering.”
  • “Why must LoginRequiredMixin come first?”
  • “When would you not use a CBV?”

Your storyScoping is the security boundary and it lives in get_queryset, not get_object — scope the wrong one and /expenses/3/edit/ edits someone else's row. The subtler half: a ModelChoiceField defaults to every row in the table, so an unscoped dropdown leaks other users' category names and lets a crafted POST file an expense against one. The mixin was extracted only after the duplication was real — six get_queryset overrides, four get_form_kwargs.

deepphase-10-api

5 · Django REST Framework

Flagged unprompted as the gap you had not noticed: a large share of Django postings are API roles, and this project was server-rendered templates only. Frappe gave you REST from the DocType, so you had never hand-built a serializer. Now closed.
What deep means
  • Serializer vs ModelSerializer; validation and validate_<field> mirroring clean_<field>
  • APIView vs GenericAPIView vs ViewSet, and routers
  • Permission classes, including object-level has_object_permission — the DRF mirror of OwnerScopedMixin
  • Authentication classes, pagination, throttling, versioning
  • Prefetching inside serializers to avoid the nested N+1
Answer cold
  • “Your ViewSet has IsOwner in permission_classes — is it safe?”
  • “Cursor or offset pagination, and what does each cost?”

Your storyhas_object_permission never runs on list. retrieve, update and destroy call get_object() so the object permission is consulted; list does not call it at all. A ViewSet whose only protection is a permission class returns every user's rows from its collection endpoint while correctly refusing them one at a time. The boundary is get_queryset() — the same answer as the server-rendered views.

6 · Migrations, beyond makemigrations

Frappe's auto-sync from DocType JSON means you have never had to think about ordering. This is the one topic where the project gives you most of the answer, not all of it.
What working means
  • Data migrations with RunPython and a reverse function; why migrations are committed
  • Squashing; resolving conflicting migrations on a shared branch
  • Zero-downtime schema change — add nullable, backfill, then make non-null, as three deploys
  • swappable_dependency and why the initial migration survived the user-model swap
Answer cold
  • “Add a non-nullable column to a table with 10 million rows, no downtime. How?”

Your storyThe GIN index over to_tsvector('english', note) is created by RunPython, not declared in Meta — a GinIndex on the model would be attempted on SQLite and fail to migrate. That is the honest shape of an index one backend cannot have.

Second story — new in phase 17Adding paid_by took five migrations and a backfill: add the nullable column, create one self-participant per user, point every existing expense at it, add the self participant to old splits so the implicit “+1” behaviour is preserved. Then it crashed — the self row was named "You", which collides with the case-insensitive unique name constraint for anyone who already had a contact called that, and a failing data migration stops the whole upgrade. Renamed to FirstName (self) with a numeric suffix.

Third story — the rule you're allowed to breakMigration 0008 was edited in place after being applied, with 0010 added to rename the rows the old version had created. Editing an applied migration is normally wrong; the written reasoning is that the old version could not have run on the databases it would fail on, and 0010 covers the ones where it succeeded. Knowing when a rule bends, and being able to justify it, is a better answer than reciting the rule.

Still to rehearseZero-downtime schema change on a live table — add nullable, backfill, constrain, as three deploys. Phase 17 gave you the backfill half; the deploy-sequencing half is still reading.

7 · Forms and validation

Already strong, and it carries one of your best stories — the kind that sounds like experience because it only happens to people who shipped something.
What working means
  • clean_<field> vs clean() vs model full_clean(); what _post_clean does
  • Formsets, widgets, initial vs instance vs data
  • Which invariants a database can hold, and which have to live in a form plus a transaction
  • Formset mechanics: empty_form and __prefix__ for adding a row, TOTAL_FORMS, the DELETE flag for saved rows vs blanking for unsaved ones, and why neither needs renumbering
  • has_changed() — it decides whether a blank extra form gets validated at all
  • form_valid and form_invalid are separate exits that share no code
  • Form-level required over model blank=False, when old rows can't satisfy a new rule

Your storyA ModelForm cannot validate a UniqueConstraint over a field the form excludes. Django skips constraints touching absent fields, and user is absent by design — so the constraint guarantees correctness while clean_name() explains it. Without the form layer a duplicate is an IntegrityError 500 instead of a field error.

Second storyAdding an inline formset changed every existing POST to the view. Without {{ formset.management_form }} Django cannot tell how many child forms came back and refuses the submission — which surfaces as the parent form apparently rejecting valid data. The symptom points nowhere near the cause.

Third story — the best one you haveFill in line items, tick who shared each, leave the note blank, submit — and every line item is gone. The POST carried all of it; the server threw it away. A CreateView has two exits after validation and they share no code: form_valid() got the formset bound to the POST, while form_invalid() fell through to get_context_data, whose fallback built a fresh empty one. The comment beside that fallback claimed form_invalid passed a bound formset — which is exactly how it survived review from phase 8 until session 22.

And the fix you refusedNo persistence was added, deliberately. sessionStorage, localStorage or a draft table would each be a second copy of state that already exists in the POST — and a second copy can disagree with what was submitted. Re-render from the request. That's the answer that shows judgement, not just a fix.

Fourth story — a rule that stopped being a gate“Items must sum to the total” used to refuse the whole submission, throwing away everything else the person had typed. Now the breach is recorded as a fact, the expense saves, the view warns — and nothing consumes an unbalanced expense, because balances() skips one rather than charging its items and leaving part of the bill owed by nobody. Frappe has no idiom for “record it, don't act on it”, which is why it takes a lost form to think of it.

8 · Testing, past what you have

357 tests means the follow-ups get sharper. The interesting answers here are about what tests cannot see.
What working means
  • TestCase vs TransactionTestCase, and why assertRaises(IntegrityError) needs its own atomic() savepoint
  • override_settings and what it cannot reach — anything evaluated at import time
  • Mocking external calls, freezing time, fixtures vs factories
  • What coverage does and does not prove; testing Celery with CELERY_TASK_ALWAYS_EAGER and why that is a partial lie
Answer cold
  • “You have 100% coverage. What can still be broken?”

Your storyThe digest command iterated users with queryset.iterator() — a server-side cursor — while committing inside the loop. The commit invalidates the cursor and user two raises InterfaceError. All sixteen tests passed with the bug present, because TestCase wraps each test in a transaction so atomic() is only a savepoint and never really commits. It surfaced only when the command was run for real. That is the clearest demonstration of why both base classes exist.

9 · Celery and background work

The phase this project exists to demonstrate — and the one where “I've used Celery” invites the question that separates users from operators.
What working means
  • Broker vs result backend; beat vs cron
  • Idempotency — the MonthlyDigest(user, month) unique constraint, claimed before the send
  • Retries, acks_late, visibility timeout, what happens when a worker dies mid-task
  • Why passing a model instance to a task is a bug, and you pass the pk
  • Every setting as a failure mode: JSON-only serialisation, prefetch_multiplier=1, autodiscover_tasks
Answer cold
  • “Your task ran twice. Why, and how do you make that harmless?”
  • “When would you not use Celery?”

Your storyThe rule worth saying out loud: reach for a queue when the trigger is a request; when the trigger is a clock, a command plus cron is usually the honest answer. CSV export is Celery because a user is waiting on a connection. The monthly digest is cron because nobody is. Both can run twice, so both have a guard — an early return on status, and a unique constraint claimed before sending.

Second storyDispatch with transaction.on_commit, never .delay() inline — the worker is fast enough to query for a row the web process has not committed yet. That is the classic Celery bug, and phase 13 found it living in the setup phase 6 had already built.

Issue 34 — the self participant is unprotected in the API

The web People pages filter out is_self; the API lists, renames and deletes it like any contact. Renaming it makes you appear under a friend's name; deleting it strands paid_by on every expense you paid. The one open item that can still break something — parked because the self-participant design may need rethinking rather than patching.

Token and JWT authentication
